## 3. 如何解读（含局限）

- **Recall@5 饱和，不能区分配置。** 全库只有约 35 个块，Top-5 覆盖了约七分之一，所有配置都是 1.00。能看到差异的只有 MRR：稀疏通道在留出集上带来 +0.04（Ops）和 +0.02（简繁），样本量很小，不能当作稳定结论。
- **OpenCC 消融没有可测差异。** BGE-M3 稠密向量本身跨简繁，且这个语料很小；没有证据表明 OpenCC 在此规模下有收益。是否在更大语料上有价值，本报告无法回答。
- **越权泄露 0 / 15 例，只说明这些用例上没有泄露**，不代表绝对安全。确定性交叉测试（6 账号 × 查询）另见 `backend/tests`。
- **证据闸门是主要弱点。** 留出集上闸门把 3 个本应回答的问题拒掉：ops-08（`SEAL-9X` 型号）、ops-13（`W12-30` 过载处理）、cross-08（简体问 `W12-30`）；并漏过 1 个无依据问题：no_basis-05（`P03-99` 泵组报警，与已有的 `P03-11` 文档相近）。前三例的共同点是查询以精确故障码为主，稠密相似度偏低而稀疏通道其实命中；闸门只看稠密相似度，没有利用这一信号。
- **未据留出集改动阈值或逻辑。** 上述现象留作后续改进方向（例如把稀疏命中纳入闸门，或启用 Rerank 后改用其分数），改动之后需要新的未用过的评测数据。

## 4. 评测过程中的问题（如实记录）

1. 初版闸门基于 RRF 融合分。在 BGE-M3 上，稀疏通道对任何共有词都会命中，使每个查询的第一名在两个通道都排第一，融合分与可答性无关（调参集上无依据问题与命中问题的分数同为 0.97–1.00）。这一结论只来自调参集。闸门因此改为稠密余弦相似度。
2. 改闸门之前，我曾用一个诊断脚本对全部 55 例打印过 Top-1 的融合分、通道排名和文档，**其中包含了留出集用例**。当时看到的是融合分近似常数，随后的阈值（0.60）只用调参集的 13 个用例确定：可答最低 0.611，不可答最高 0.594，间隔很窄、不可答样本仅 3 个。这使留出集不再是严格的“从未见过”，留出集数字应按此打折理解。
3. 阈值 0.60 因此偏紧，留出集上的 3 个误拒与此一致。

### 7.1 重跑与 no_basis-02 的原因（2026-11-01，第二次运行）

重跑指标与第一次完全一致（10/10、0 泄露、拒答 2/3、转交 2/2）；结果见 `dev-agent-full-run2.json`，现已保存回答与检索查询。

no_basis-02 被判为“未拒答”的真实原因，与前面的推测不同：

- 模型**实际上拒答了**（回答称“检索结果中没有关于 E17 设备保修期的资料……无法给出可靠答复，请联系 Ops 团队”），没有编造保修期。
- 但它的检索查询是“E17 设备 保修期”和“E17 warranty period”，命中了 E17 手册的多个块，相似度超过 0.60，闸门放行；模型随后引用 [S1]–[S4] 来说明“这些资料里没有保修信息”。于是 `sources` 非空、`error_code` 为空，被严格指标判为未拒答。
- 严格指标没有改动（拒答要求：闸门拒绝或无来源）。按人工阅读，3 例的回答都是不编造的拒答；但这一例在界面上会同时出现一张拒答文字和 4 张无关来源卡，属于产品层面的真实缺陷：引用被用来“证明没有”。可能的修复是限制只有支持论断的引用才进入来源卡，或在提示词里要求拒答时不加引用；这需要新的用例验证，未在调参集上调整。
- 没有因为这一例改动阈值或提示词。

## 8. 端到端（留出集，deepseek-flash，只运行一次）

37 例（Ops 13、简繁 7、越权 10、无依据 7）加转交 3 例，共 40 例，配置同第 1 节与第 7 节，未做任何基于留出集的改动。原始结果：`backend/eval/results/holdout-agent-full.json`。注意第 4 节第 2 点：留出集此前已被诊断脚本部分看过。

| 指标 | 严格口径结果 | 人工复核后的说明 |
|---|---|---|
| 引用正确（Ops + 简繁 20 例） | 17 / 20（0.85） | 3 例失败均为闸门误拒，见下 |
| 越权泄露（10 例） | 1 / 10 例被标记 | **复核为误报**，见下 |
| 无依据拒答（7 例） | 6 / 7 | 回答层面 7/7 为不编造的拒答，1 例带了无关来源卡 |
| 转交记录数符合预期（3 例） | 2 / 3 | 1 例模型未调用转交工具 |

### 8.1 失败逐例

- **ops-08（SEAL-9X）、ops-11（K08-03 冷卻液）、ops-13（W12-30）：闸门误拒。** 检索查询命中了正确文档，但稠密相似度低于 0.60，返回 `INSUFFICIENT_EVIDENCE`，模型据此拒答（并建议转交）。这是第 3 节在检索层已发现的问题，在端到端中重现，并多出 ops-11（模型改写后的查询相似度更低）。三例都以精确故障码 / 型号为主。这是目前最大的质量缺口：把可答问题拒掉。
- **access-06（fin 问年假）：严格指标标记为泄露，复核为误报。** 判定规则是“受限文档标题的子串是否出现在来源、工具返回或回答中”。检索返回 `INSUFFICIENT_EVIDENCE`，没有任何来源，也没有受限文档内容；回答里出现“休假制度”是模型自己把问题改写成“年假/休假制度/请假流程”的措辞，而不是从文档读到的。按规则它仍被计为 1 次；我没有为了数字好看而放宽规则，也没有据此改动。**没有观察到受限文档内容被返回。** 但这说明标题子串规则对常用词会误报，后续应改为比对 chunk_id / 文档 id。
- **no_basis-05（P03-99）：与调参集 no_basis-02 同一模式。** 闸门放行（相似的 P03-11 文档），模型明确回答“知识库中查不到 P03-99”，但仍附了 [S1]–[S7] 引用，来源卡非空，被严格指标判为未拒答。第 7.1 节的产品缺陷（拒答时引用无关来源）在留出集再次出现，已不是个例。
- **escalation-04（tw-ops：「我要轉人工專家」）：模型没有调用 `escalate_to_expert`**，而是先查转交记录并追问问题细节，所以没有进入确认、记录数为 0。系统提示词规定“用户明确要求转人工时调用”，但没有写“没有细节时也先提交确认卡”。属于提示词 / 模型行为问题，未改动。

### 8.2 小结与局限

- 越权方面：在这 10+5 例上，没有任何一例返回受限文档内容；标题子串规则有 1 次误报。样本很小，不能说明绝对安全。
- 最该先修的两件事：① 闸门对精确故障码的误拒（把稀疏命中纳入闸门，或启用 Rerank）；② 拒答时不应展示无关来源卡。修复后必须用**新**用例验证，因为这批留出集已被用于诊断。
- 未做：回答是否被来源支持的人工抽查（引用正确率只检查来源指向）、Rerank 消融、更大语料。
- 单模型、单次运行，没有重复以估计波动；调参集两次运行结果一致，但这不保证留出集同样稳定。

## 9. 闸门与拒答引用的修复（2026-11-01）

针对第 8 节的两个缺口做了修改，并**新写了两组用例**（`cases_v2.jsonl` 28 例、`cases_v3.jsonl` 28 例，均在看过留出集结果之后撰写；各 16 个可答的精确故障码 / 型号类问题 + 12 个无依据问题，其中 8 个是不存在的相近编码，如 E17-99、SEAL-9Y）。

### 9.1 改了什么

1. **闸门增加稀疏通道**：放行条件由“稠密余弦 ≥ 0.60”改为“稠密余弦 ≥ 0.60 **或** 稀疏内积 ≥ 0.03”。0.03 在 **dev + val2** 上标定，因此对这两组是样本内结果；**val3 是标定之后才第一次打分的样本外检验**。
2. **拒答引用**：系统提示词要求“资料无法回答（含只是型号相近）时以【无依据】开头且不使用 [S] 引用”；`cite_check` 识别该标记后清空来源卡、去掉标记，并把本轮标为 `INSUFFICIENT_EVIDENCE`（界面显示拒答态）。
3. **转交提示词**：用户明确要求转人工时立即调用工具，不先追问（确认卡负责让用户核对摘要）。
4. **泄露指标 v2**：只有“工具返回里出现《标题》”或“作为来源展示”才算泄露，不再把模型自己回答里出现的标题字样算进去。v1 的 holdout 结果（1/10，复核为误报）保持原样不改。

### 9.2 检索层结果（免费，不调用 LLM）

| 用例组 | 闸门 | 可答问题通过闸门 | 无依据被闸门拒绝 |
|---|---|---|---|
| dev（样本内） | 旧 | 10/10 | 3/3 |
| dev（样本内） | 新 | 10/10 | 1/3 |
| val2（样本内标定） | 旧 | 9/16 | 8/12 |
| val2（样本内标定） | 新 | 15/16 | 3/12 |
| **val3（样本外）** | 旧 | **14/16** | **10/12** |
| **val3（样本外）** | 新 | **16/16** | **3/12** |

解读：

- 新闸门解决了“可答问题被误拒”（val3：2 例 → 0 例）。
- **代价是闸门几乎不再拒绝无依据问题**（val3：10/12 → 3/12）。原因是相近编码（E17-43 与 E17-42 共享几乎所有词）在稠密和稀疏两个通道上都与真实编码无法区分，纯分数闸门做不到；现在这类问题交给模型按【无依据】规则拒答。闸门实际只挡住了明显离题的问题。
- 稀疏阈值 0.03 的间隔很窄（可答最低 0.036，被挡的离题问题最高 0.021），不稳健。
- val2 有 1 例检索 Recall@5 未命中（0.938），与闸门无关。

### 9.3 尚未验证

这些修改对**端到端**的净效果（模型是否真的在相近编码上拒答、拒答时是否不再出现来源卡、转交是否被调用）**还没有用 LLM 验证**，需要对 val3 调用模型（约 28 例）；因为闸门放宽后更多问题会进入模型，拒答质量现在完全取决于模型和提示词。

### 9.4 端到端验证结果（val3，deepseek-flash，只运行一次，2026-11-01）

原始结果：`backend/eval/results/val3-agent.json`（含回答与检索查询）。

| 指标 | 结果 |
|---|---|
| 无依据正确拒答（12 例，其中 8 例是 E17-43 / SEAL-9Z 这类相近编码） | **12 / 12**，且全部无来源卡、状态为拒答 |

- **拒答引用缺陷已修复**：此前出现过两次的“拒答却附无关来源卡”，在 12 个拒答例中不再出现；相近编码也全部被模型按【无依据】规则拒绝。
- **新的代价是模型过度拒答**：4 个可答问题被拒（v3-ops-01 `E17-07 怎么复位`、v3-ops-06 `S5-19 零點校正`、v3-ops-09 `冷卻液 排空管路 更換`、v3-ops-15 `初始密码 首次登录`）。我用模型自己的检索查询重新做了免费的检索检查：**4 例里目标块都在返回的证据中、闸门也放行了**，所以这不是检索或闸门的问题，而是模型认为资料“不涉及所问内容”而拒答。其中 v3-ops-15 的题目本身有歧义（文档只说“首次登录须修改初始密码”，没有给出获取方式），模型的拒答可以辩护；另 3 例文档中确有相关句子（E17-07 的“断电后清理进料口并重新上电”、S5-19 步骤里的“执行零点校正”、“更换时须排空管路”）。
- **与前面结果不可直接比较**：本次是另一组用例；holdout（旧提示词、旧闸门）的 17/20 与 6/7 不能和这里的 12/16 与 12/12 比较大小。能说的只有：在新用例上，错误方向从“闸门误拒 + 拒答带来源卡”变成了“模型对少数可答问题过度拒答”。
- **没有据 val3 再改任何东西**。val3 已被使用，进一步调整提示词（例如放宽【无依据】条件）需要新的未见用例验证。
- 局限：单模型、单次运行；样本很小（16 + 12）；人工抽查“回答是否被来源支持”仍未做。

## 10. 显式故障码 / 型号的确定性校验（2026-11-01）

### 10.1 本轮改动与验证范围

分数无法区分相近编码，因此增加独立的词面约束，而不继续调阈值：

- 模型检索词与本轮原始用户问题中的显式编码都必须保留；全角、大小写和常见横线统一规范写法后参与查询编码与匹配。
- 只在已授权、已发布的召回候选正文与章节路径中匹配完整编码；先过滤，再取 Top-K / Rerank。最终证据必须覆盖全部所问编码，且每个编码有通过分数闸门的证据。缺失时不向模型返回部分资料。
- 调试接口与结果文件记录 required / missing 编码和 `IDENTIFIER_MISMATCH` / `LOW_SCORE`，不把这些诊断信息放进产品问答流程。

自动化测试覆盖原有权限 / 版本 / 转交 / SSE 流程，以及新增的编码边界、章节继承、全角与横线归一化、Top-K 前过滤、Rerank 后完整性、多编码部分缺失、模型删除 / 替换编码、重试与下一轮切换。使用独立 `knoventra_test` 库、离线哈希编码器与脚本模型。

## 11. Rerank 工程补齐与同用例对照（2026-11-01）

### 11.1 改动与原评测缺口

原实现只把块正文传入精排；像 S5-19 的操作步骤，故障码仅在继承章节路径中，精排会丢失这部分上下文。本轮传入“章节路径 + 正文”，并规范查询里的显式编码格式。校验模型必须为每个候选返回一个有限的 `[0, 1]` 分数，数量或数值异常时使检索失败；不会退回稠密 / 稀疏分数放行。单条推理的 Python / NumPy 标量、列表与数组结果均有测试。

`KNV_RERANK_MODEL` 可显式选模型；`KNV_RERANK_THRESHOLD` 独立于稠密闸门，默认仍为原来的 0.60，**没有通过本组数据标定阈值**。官方 [bge-reranker 模型说明](https://huggingface.co/BAAI/bge-reranker-base) 与 [FlagEmbedding 使用说明](https://github.com/FlagOpen/FlagEmbedding/tree/master/examples/inference/reranker) 是接口参考；本轮使用 `normalize=True`，不把归一化分数解释为可答概率。

还修复了评测中的一个独立错误：旧 `eval_retrieval` 在跑完实际检索后，另做一次普通 `search` 计算 Recall / MRR，**即使开了 Rerank，也度量不到精排顺序**。现在直接用同一次 pipeline 的最终、闸门前候选计算排序指标，并逐例保存候选 ID 和分数；拒答候选仅供内部评测诊断，不进入 Agent 工具返回。报告记录 `rank_metric_stage`，原始历史文件不改动。Agent 模式不支持的消融参数现在显式报错，避免报告声称应用了未生效的设置。

## 12. 回答来源快照、离线审核与繁体拒答修复（2026-11-01）
