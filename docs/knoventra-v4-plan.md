## 2. 场景与虚构数据

### 2.1 业务场景

虚构的“示例精密设备公司”在 CN、TW、SG 三地派驻现场工程师，为客户安装和维护晶圆清洗机台。工程师每天按固定模板填写技术日志，公司还维护一张技能掌握矩阵。主线故事如下：

1. **经验检索**：`sg-ops` 问“WX-38 切换 tank 时报 alarm、pump 不转怎么办”。系统召回历史排障记录和对应 SOP，回答注明日期、机台、来源。
2. **机型澄清**：用户只问“spindle 更换扭矩多少”。单面机型和双面机型的答案不同，系统先追问机型，不混着回答。
3. **拼写与编号**：用户问“mix tank trouble shotting”或直接报 SOP 编号，也能正确命中。
4. **人员查询**：用户问“谁会做 golden check”，系统走技能表的结构化查询，不走 RAG。
5. **求助单**：查不到可行方案时，系统多轮补齐机台号、告警、已尝试步骤，弹出确认卡，建单（幂等），并推荐掌握该技能的工程师。
6. **跟进与沉淀**：专家受理并填写解决方案，提问人可以查到状态变化；结案后生成案例草稿，经审核发布到案例库，再问同样的问题就能直接命中。
7. **记忆**：长对话自动压缩；隔天回来问“上次那个 alarm 后来怎么解决的”，系统能召回；如果当时引用的手册已被撤销，就不再复用它。

### 2.2 数据（全部虚构，由脚本确定性生成）

- **日志**：`data/demo/journals/*.xlsx`，表头为“仪器编号、日期、技术员、工作主题、工作内容、注意事项、公司名称”，约 200 行，6 名工程师、3 个机型（单面 `WX-38`、双面 `WX-P`、`ST-250`）。
- **技能矩阵**：和日志混排在同一张表里，复用同样的七列：日期为空，工作主题填技能项，工作内容填“作业次数：N；掌握程度：X”（不了解 / 了解 / 掌握）。内容是工程师 × 机台 × 技能项。
- **SOP**：约 10 份，编号格式 `SOP-xxx-xxxxxx-xxx`，其中 2 份按机型分节，1 份有 v1 / v2 两个修订。
- **故意注入的难点**，每类至少 3 例，并在生成清单中标注：
  - 术语拼写错误（如 shotting、chamical、tecahing）和中英混写
  - 周报复制粘贴造成的近似重复行
  - 未解决的排障记录（“待跟踪”）
  - 机型不同、答案不同的操作
  - 混入正文的口令、电话等敏感串，用于测试脱敏
- 生成脚本不调用模型；数据和清单一起版本化。真实公司资料不进仓库。

## 3. 架构变更

```
提问 ─► query_plan（重写 / 拆分 / 意图 / 机型）
          ├─ case/sop/policy ─► 混合检索（ES + dense + sparse → 加权 RRF → 回表校验 → Rerank → 闸门）
          ├─ skill_lookup ────► 技能表结构化查询
          ├─ help_status ─────► 求助单查询
          └─ 无可行方案 / 明确求助 ─► 槽位收集（Redis）─► interrupt 确认 ─► 幂等建单 ─► 推荐专家
所有工具经 MCP 客户端调用独立的 MCP 服务；上下文由记忆组装器按 Token 预算拼装。
```

### 3.1 入库（G1）

- **模板适配**：按表头名称定位列，列顺序变化和多余列都不影响；缺少必需表头时整表拒收并报出缺失项。
- **行级记录**：每行是一条记录，元数据包括机台号、机型、日期、技术员 ID、公司、区域。机型用字典抽取，抽不到就标为 `unknown`，不猜。
- **去重**：精确重复按归一化文本的哈希判定；近似重复用 SimHash 加阈值判定，合并成一条并保留所有日期。重复入库是幂等的。
- **脱敏**：在入库链路上按规则替换口令、电话等敏感串，替换前后的计数写入审计，原文不落库。规则命中的样例写成测试。
- **案例字段**：从排障类记录中抽取现象、告警、原因、解决方法、是否解决。默认用规则加关键词；LLM 抽取作为可选开关，开启前需单独授权付费调用。
- **技能表**：进入结构化表 `knv_skill`，不切块、不向量化。

### 3.2 Elasticsearch 通道（G2）

- **部署**：Compose 中增加 ES 8.x，使用固定 digest 的自建镜像并安装中文分词插件（首选 IK，镜像构建失败时退回官方 smartcn）。测试用独立索引，按测试运行清理。
- **映射**（按实现更新）：
  - `text`：索引时用 `ik_max_word`，查询时用 `ik_smart`。拼写纠错表在索引和查询两侧都生效；领域同义词用 `synonym_graph`，只在查询侧。英文的模糊匹配放在 `text.latin` 子字段（standard 分词，`fuzziness: AUTO`），因为 fuzziness 不能经过图同义词。索引和查询都用 OpenCC 简体化后的文本。
  - `identifiers`：`keyword` 字段（大写归一），存 SOP 编号、阀门号、告警码，查询时用 terms 加权。
  - `filter` 子句只有 `kb_id` 和 `revision_status`。`machine_model` 只写入索引，不参与过滤；机型过滤安排在 D7，在 PG 回表后按分块机型过滤。`region` 不建索引，区域权限已经由 KB 授权（`kb_id` 过滤）覆盖。
- **同步**：PG 是唯一事实源。`publish()` 在改状态的同一事务里写事务性 outbox（`knv_es_outbox`）；提交后 drain 按 PG 当前状态重算该文档在 ES 中的分块。drain 只删除仍是读取时 `enqueued_at` 的 outbox 行，所以并发发布不会被吞掉。失败时保留 outbox 并记录错误，由 `reconcile`（按分块 ID 双向对账）补齐；`rebuild` 换别名后也会再对账一次。
- **防越权**：ES 查询自带权限和版本过滤，融合前再按 chunk ID 回到 PG 校验 `PUBLISHED` 和可读 KB。这样即使 ES 里残留旧数据，也不会进入融合结果。测试中故意让 ES 留着旧修订和不可读的分块，验证它们被挡下。
- **降级**：ES 超时或不可用时，用 dense、sparse 和编号精确通道 `ident` 三个 PG 通道继续检索，并在检索轨迹里写明 `es_unavailable`，不报错、不放宽权限。
- **查询**：ES 用本次实际执行的查询（改写或子查询），用户原话里的编号通过 `identifiers` 一并带上。

### 3.3 加权 RRF

- 公式改为 `score = Σ w_c / (k + rank_c)`，通道权重在配置里设置。
- 按查询类型设置两套权重：带编号的查询提高 ES 权重，自然语言查询提高稠密通道权重。
- 只在 dev 集上调权重，在冻结的留出集上报告一次结果，不反复调。等权方案保留作为对照组。

### 3.4 查询理解（G3）

- 在 `agent` 之前加一个 `query_plan` 节点，用结构化输出产生：改写后的查询（结合历史补全指代，用纠错表归一化拼写）、最多 3 个子查询、意图（`case_sop` / `policy` / `it_guide` / `skill_lookup` / `help_status` / `chitchat`）及置信度、机型。
- **路由**：意图决定检索哪些 KB；置信度低于阈值时退回全部可读 KB。路由只能缩小权限范围，不能扩大。
- **机型澄清**：命中的 SOP 有机型分节而用户没说机型时，先追问，不检索。
- 节点失败或超时，就退回 v3 的行为（模型自己生成检索词），并在轨迹里记录。
- 测试用假模型覆盖每个分支；评测中记录路由准确率。

### 3.5 求助单（G4）

- **数据**：新表 `knv_help_request`，字段包括申请人、机台号、机型、告警、现象、已尝试步骤、证据引用、负责人、解决方案、幂等键，状态为 `OPEN → ASSIGNED → IN_PROGRESS → RESOLVED → CLOSED`（另有 `CANCELLED`）。新表 `knv_help_event` 是只追加的审计流水。现有 `Escalation` 迁移为 `kind = expert_escalation` 的求助单，接口保持兼容。
- **槽位收集**：必填字段缺什么就追问什么，槽位草稿存在 Redis 工作记忆中（见 3.7）。用户随时可以说“算了”取消。
- **确认与幂等**：沿用现有的 interrupt 确认卡和 `operation_id`。确认卡显示所有槽位，让用户核对。
- **专家推荐**：只考虑技能矩阵中对该技能“掌握”的工程师，排序依据依次是同区域优先、当前未结单数少者优先；没有合适人选时进入待派单队列。推荐理由显示在确认卡上。
- **状态机**：状态流转只允许合法边，由服务端校验；专家接口可以受理、更新进度、提交解决方案；每次变更写一条事件流水。
- **跟进**：提问人通过工具或页面查看状态和最新事件；回到原会话时，系统提示“你的求助单已更新”。（截至 D10：“我的求助单”页面和 `get_escalation_status` 已可查看状态；回到原会话时的更新提示尚未实现。）
- **结案沉淀**：求助单 `RESOLVED` 后生成案例草稿（现象、原因、解决方法、来源求助单），由审核人在管理页发布到“案例库”KB，走现有的修订与发布流程，之后可被检索。
- **前端**：新增“我的求助单”和“专家工作台”两个页面；专家工作台可以只做列表加详情。

### 3.6 MCP（G5）

- **服务**：新进程 `backend/src/knoventra/mcp_server/`，用 Python `mcp` SDK 和 streamable HTTP，提供 `search_knowledge`、`lookup_skills`、`get_help_request`、`prepare_help_request`、`submit_help_request` 五个工具。仓库根目录的 Java `mcp-server/` 是上游参考代码，保持不动。
- **客户端**：Agent 端用 `langchain-mcp-adapters` 加载工具。测试中保留进程内替身，保证 CI 不依赖外部服务。
- **身份**：每次运行由 API 签发一个短期 JWT（受众是 MCP 服务，内容包括 `user_id`、运行 ID、过期时间），通过 HTTP 头传递。MCP 服务验签后重新计算 AccessScope。工具参数里没有任何身份字段，模型无法伪造。
- **写操作两段式**：确认发生在 LangGraph 的 interrupt 里；`submit_help_request` 必须带上已批准的 `confirmation_id`，MCP 服务在执行端再查一次数据库确认它属于本人、已批准、未过期，然后按幂等键建单。也就是说，执行端会做第二次鉴权。
- **测试**：伪造或过期的 token、他人的 `confirmation_id`、重放提交、MCP 服务重启。

### 3.7 分层记忆（G6）

| 层 | 存储 | 内容 | 生命周期 |
|---|---|---|---|
| 持久图状态 | PG Checkpoint（已有） | 消息、待确认操作 | 随会话 |
| 短期工作记忆 | Redis，键为 `knv:wm:{user_id}:{thread_id}` | 滚动摘要、槽位草稿、当前任务与意图、最近提到的机台和机型 | TTL 24 小时，每次访问续期 |
| 长期情景记忆 | PG `knv_episode` + pgvector | 已解决的问题或结案求助单的摘要，以及引用的 chunk / 文档 ID | 按用户隔离，可删除 |
| 用户画像 | PG `knv_profile` | 语言偏好、常用机型和机台（按使用频次统计）；部门、区域只读，取自用户表 | 长期 |

- **Redis 的定位**：Redis 只是工作记忆和缓存，不是唯一事实源。Redis 丢失时，槽位从 Checkpoint 中的最后一次确认卡和消息重建，摘要重新生成。这条要有专门测试。（D11 实现：消息侧的持久记录是 `request_help` ToolMessage 的 `artifact`；Redis 副本带锚点，与 Checkpoint 不符就重建。）
- **压缩**：历史超过 Token 预算（可配置，默认 6k）时，把较早的轮次压缩成摘要写入 Redis，保留最近 N 轮。槽位和待确认操作固定保留，不参与压缩。记录压缩前后的 Token 数。
- **情景召回**：每轮开始时按当前问题召回该用户最相关的 3 条情景记忆。注入前逐条检查它引用的文档当前是否仍然可读、是否仍是已发布版本；不满足的整条丢弃，并记在轨迹里。
- **画像使用**：画像只用于预填槽位和设置回复语言，不参与权限判断。（D12 实现：不直接预填，改为在工具结果里提示常用机台并追问用户；见 DECISIONS 第 74 条。）
- **上下文组装**：在预算内按优先级拼装：系统提示 > 槽位与待确认操作 > 画像 > 情景记忆 > 滚动摘要 > 最近轮次 > 本轮证据。超出预算时，从低优先级开始截断。

## 4. 评测

- **新评测集**（约 40 例，随数据一起版本化，划分为 dev 和冻结留出集）：拼写错误、编号、机型澄清、近似重复、一句多问、技能查询、求助状态、指代追问。
  - 已完成的检索层集合 `cases_field_v1.jsonl`（39 例）覆盖：编号、拼写错误、同义词与中英混写、繁体、机型差异答案、历史案例（含近似重复的多样性对比）、普通问法和越权。机型澄清、一句多问、技能查询、求助状态、指代追问属于 Agent 层行为，要等付费的 Agent 评测，目前没有测量。
- **检索层**（离线，不调用付费模型）：
  - 召回率@5 和 MRR，比较 pgvector 两通道、加入 ES、加权 RRF 三种配置
  - 去重对 Top-K 多样性的影响
  - 改写开和关的对比
- **Agent 层**（付费调用，每批单独获批）：路由准确率、澄清触发率、求助单槽位完整率、在重试和刷新下重复建单数为 0。
- **记忆**：压缩前后的 Token 数和关键槽位保留率；撤权后情景记忆复用为 0。
- 报告中只写实测值，并注明数据规模；没有测过的不写数字。

## 5. 三周计划

顺序是数据 → 检索 → 业务闭环 → 记忆和 MCP。后面的步骤依赖前面的数据和检索；MCP 放在最后，是为了把已经稳定的工具整体迁移过去。

### 第 1 周：数据与混合检索
- **D1**：虚构数据生成脚本、模板适配、技能表入库。✅ 2026-11-23：`data/demo/generate_journals.py` 生成三地日志（206 行，含 3 行精确重复、3 行近似重复）与技能行 156 条；`knoventra.ingestion.journal` 按表头定位列，并区分同表混排的日志行与技能行；`knv_skill`（迁移 0007）幂等 upsert。SOP 文档未在 D1 生成，移到 D2。
- **D2**：脱敏、精确去重和近似去重、机型抽取、案例字段规则抽取。✅ 2026-11-23：`knoventra.ingestion.cases`：口令、电话、邮箱规则脱敏，审计记“命中数 / 替换后残留数”；机型先查资产登记表 `machines.json`，再用别名字典，都没有就留空；精确去重用归一化文本哈希，近似去重用 SimHash（≤10）粗筛、3-gram Jaccard（≥0.6）复核，且只在同机型内合并；案例字段规则抽取。演示数据 206 行 → 44 个案例，没有跨场景合并。结果存入 `knv_journal_case` 与 `knv_ingest_audit`（迁移 0008）。10 份 SOP 放在 `data/demo/docs/sop/`，D4 起并入默认种子。
- **D3**：Compose 加入 ES，自建分词镜像，完成映射、同义词和纠错表、发布与撤销同步、对账命令。✅ 2026-11-23：`deploy/elasticsearch/Dockerfile`（ES 8.15.3，基础镜像固定 digest，IK 插件校验 SHA-256），compose 服务 `es` 在 59200 端口；不需要退回 smartcn。实测 IK 会把繁体切成单字，所以索引和查询都用 OpenCC 简体化后的 `text_norm`。纠错表在索引和查询两侧都生效，同义词只在查询侧（`synonym_graph`）；映射哈希写进物理索引名，经别名访问。同步走事务性 outbox（`knv_es_outbox`，迁移 0009）：发布时在同一事务入队，提交后 drain 按 PG 当前状态重算 ES；失败保留在 outbox 并记录错误。`python -m knoventra.search_es.sync drain|reconcile|rebuild` 负责补齐、双向对账和换别名重建。outbox 不加外键，文档删除后仍能清掉 ES 里的副本。ES 测试连不上时会跳过，CI 的 ES job 留到 D14。

## 7. 风险

| 风险 | 应对 |
|---|---|
| 分词插件与 ES 版本不匹配，或在 Windows Docker 上构建失败 | D3 上午先验证镜像，失败就切到 smartcn，在 DECISIONS 中记录 |
| ES 与 PG 不一致导致越权 | 回表校验是硬约束，有专门的残留测试 |
| interrupt 与 MCP 写工具的配合 | 确认只在图内完成，MCP 端只认已批准的 `confirmation_id` |
| Redis 被当成事实源 | 明确它只做工作记忆；丢失重建有测试 |
| 范围膨胀 | 严格按可砍清单执行；每天结束时更新本计划的状态行 |
